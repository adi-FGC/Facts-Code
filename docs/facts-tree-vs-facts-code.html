Two codebases. One idea: turn a repository into trustworthy, agent-ready architectural context. facts-tree proved the idea works in a single afternoon-sized CLI. Facts-Code is the ground-up rebuild that turned a brutal code audit into a real platform. Here's what changed, why, and what it means for the team you're inheriting.

If you read one thing

The 90-second version.

  • Same DNA

    Both tools answer the same question: "what is this codebase, and can an AI safely act on it?" v0 already had a dependency graph, cycle & orphan detection, route & secret & TODO scanning, a docs index, and a "Copy for LLM" button. The concept didn't change.

  • v0 · facts-tree

    A brilliant, working prototype — one command, one self-contained HTML viewer, one AI-readable project-tree.json, almost no dependencies. It proved the value in the simplest possible form. A 2026 audit then scored it 123/200: great bones, real debt.

  • v2 · Facts-Code

    A ground-up re-architecture into a 19-package TypeScript monorepo: typed contracts, an engine that runs in Node and the browser, two separate artifacts (one for humans, one for AI), an ~80%-cheaper "FactsPack" context format, a 13-tool MCP server, and a real dashboard.

  • The bridge

    Not a whim. A formal code audit + an architecture proposal (10 "deepening" modules) sit between the two. Facts-Code is, almost line-for-line, that proposal executed.

  • The irony

    facts-tree calls itself "v1.0.0" (but scored 123/200). Facts-Code calls itself "v0.1, alpha" — yet it's far more mature. Version numbers lie; architecture tells the truth.

The lineage

How a viewer became a platform.

The two projects aren't rivals — they're parent and child. Reading the audit artifacts left inside facts-tree, the storyline is unmistakable.

ORIGIN

"Project Tree Viewer" — the original

A local-first Node CLI + browser viewer + MCP server. It scanned source, docs, routes, imports, exports, TODOs, git, and dependencies, then served an interactive viewer and wrote an AI snapshot. The ambition was already "agent-ready context," not just "show files."

2026-05-19 · THE AUDIT

A 200-point design & code audit123 / 200

No fatal bugs — but real cracks: test-fixture routes leaking in as "real" app routes, a symlink path-bypass in the local server, a side-effecting GET /api/scan, a mobile-broken UI, and 1,000+ line files. The verdict: strong product shape, fragile trust & structure.

2026-05-19 · THE PROPOSAL

Ten "deepening" modules

An improve-codebase-architecture pass proposed concentrating scattered logic behind real seams: a Path-Access module, File-Role classification, a Scan Session, Finding Views, shared MCP read-models, a Release Surface, and more. A blueprint for a rebuild.

NOW · THE REBUILD

Facts-Code — the proposal, executed

Rather than patch the prototype, the team rebuilt the idea as a typed, isomorphic monorepo. Every "deepening" recommendation became a package or a contract. (facts-tree lives on as the lean line, still a full CLI + server + MCP + viewer, just flat and untyped.)

Net-new in v2

Capabilities the prototype never had.

Beyond the re-architecture, Facts-Code grew genuinely new muscle — including two features added in the most recent work.

⚖️

Change Verdict

One opinionated risk headline per code change — new secrets, CVEs, cycles, and blast radius fused into a severity, for a PR or an AI reviewer.

📚

Docs intelligence

Flags every doc/spec file and parses it — headings, checklists, diagrams — into a Docs tab with todos, verifiable roadmaps, and rendered previews.new this cycle

🎨

CSS / styling audit

Audits the scanned project's CSS — specificity, conflicts, responsive device coverage, lightningcss fallbacks — in a collapsible suggestions panel with a live ticker.new this cycle

📦

FactsPack

A line-oriented wire format that hands an AI the same facts at roughly one-fifth the token cost of JSON — then ships only deltas.

🛡️

Supply-chain & secrets

Dependency manifests matched against OSV/CVE data, license risk, and an entropy-gated secret scanner that never emits a raw key.

🧠

Memory & calibration

A 2–10 KB cold-start brief, plus an append-only ledger that can measure whether an AI agent is actually trustworthy in your repo.

An honest balance

What each generation still does best.

Newer isn't strictly better. A sharp CTO keeps the prototype's virtues in view.

facts-tree still wins on

Simplicity & time-to-value

  • One command, one file. Scan → an interactive HTML you can email. No build, no monorepo, no install friction.
  • Near-zero dependencies. Three parser libs; the output runtime ships no framework.
  • Tiny surface. ~10K lines a single engineer holds in their head in an afternoon.
  • Legible. When it breaks, you read ten files, not nineteen packages.
Facts-Code wins on

Correctness, reach & extensibility

  • Trustworthy by construction. Typed contracts + role-aware findings fix the audit's leakage class of bug.
  • Runs everywhere. One engine across CLI, CI, browser, and MCP — no parallel implementations to drift.
  • Built to grow. New features (Change Verdict, Docs, CSS) snap onto one contract additively.
  • AI-economical. FactsPack + MEMORY.md make agent usage cheap at scale.
The one risk worth naming: the rebuild's power has a cost — a monorepo, a build step, an alpha version, and docs that lag the code. The audit's warning to not lose the "five-seconds-to-value" simplicity is the thing to keep watching. Facts-Code is more capable; it must stay as easy to start as facts-tree was.
Reverse lessons · the path back

What Facts-Code should steal back from facts-tree.

The rebuild won on architecture. But the prototype still beats it on the one metric that decides adoption: the first thirty seconds. Reading v0's real source — server.mjs, telemetry.mjs, copy-llm.mjs — turned up eleven concrete things worth porting, from one-click agent context to a hardened local-server security posture (and a telemetry module v0's own roadmap still lists as "todo"). Grouped now · next · later, with the engineering lift noted on each.

Now · highest leverageUI

1 · Beat v0's copy button: a self-refreshing agent skill

v0 puts a prominent Copy for LLM button in the chrome (copy-llm.mjs) — two modes, a live token + KB estimate, a toast — but it's a one-shot blob pasted into a chat. v2 should go further than copying. Path: a one-click "Set up FACTS for agents" that installs the skill if absent (export-skills → SKILL.md / .cursorrules / AGENTS.md / copilot-instructions.md) and ships a contract telling the agent to keep .facts/agent.pack fresh on every edit (factstack watch / a hook), read that pack for context, and edit from it instead of re-scanning. Lift: ~1–1.5 days — the skill emitter + watch already ship; this wires them into one action and upgrades the skill's instructions.

Now · highest leverageUI

2 · A "5-second" instant mode

v0's crown jewel: facts-tree . pre-scans, caches the rendered HTML, and serves it on the first request (cachedHtml handed from bin into server.mjs); --html skips the server entirely — self-contained file to temp, browser opens, process exits. v2's first-value path drags the monorepo behind it. Path: ship factstack quick [path] over the existing static export — the "try it now" on-ramp that graduates into the full dashboard. Lift: small–medium — packaging, not engine work.

Now · highest leverageDX

3 · Idle auto-shutdown

v0's server kills itself when idle: resetIdle() re-arms a timer on every request (5 min when launched at a path, 30 min as a picker) and calls process.exit(0). No orphaned localhost servers — ever. Path: copy the idle timer into any factstack serve mode. Lift: small — ~15 lines that retire the "did I leave a server running?" tax (we left one on :5055 mid-audit).

Now · highest leverageAPI

4 · Dependency freshness

v0's /api/deps-outdated checks every dependency against the npm registry's latest dist-tag and returns {current, latest, isOutdated} — 3-second timeout, offline-tolerant. v2 maps the dependency graph but never asks "how far behind are we?" Path: a freshness scanner feeding an "N outdated" chip on the dashboard. Lift: medium — a genuinely new capability with high executive signal.

NextUI

5 · Open in editor / Claude / Codex / terminal

v0's /api/exec launches a whitelisted editor or a terminal at any file — spawn with arg-arrays (never a shell string), per-OS terminal fallback ladders, shell-metachar rejection. The whitelist already ships claude and codex entries. Path: when the dashboard is CLI-served, expose the same safe launch from file rows — and lead with one-click "Open in Claude / Codex." Lift: medium; reuse v0's whitelist plus the audit's symlink-safety fix verbatim.

NextUI

6 · The folder switcher, properly

v0 pairs /api/recent (last 10 in ~/.facts-tree/recent.json) with /api/browse — a server-backed directory walker that skips node_modules/dist/.git, detects project roots (package.json, Cargo.toml, go.mod…), and offers parent/home nav. Path: enrich the dashboard's OpenModal with recents + server browse, and make the path bar itself the change-folder affordance (v0's most discoverable pattern). Lift: medium.

NextAPI

7 · Per-file git history

v0's /api/file-history runs git log --follow -10 for one file (execFile, 5-second timeout, traversal-guarded) and returns the commits that touched it. v2 already does a repo-level git scan — this is the on-demand, per-file depth. Path: a "Recent commits" strip in the file detail panel. Lift: small–medium.

NextDX

8 · A local-server security template

Whatever ends up serving the dashboard, steal v0's server.mjs posture wholesale: 127.0.0.1-only bind, an Origin/Host allowlist on every request (DNS-rebind / CSRF defense), a validatePath() blocklist (/etc, C:\Windows…), shell-metachar rejection, and a 1 MB body cap. Path: make this the baseline of factstack serve, not an afterthought — it's the precondition for cards 5–7. Lift: small — copy, don't reinvent.

Later · evidenceDX

9 · Local-first, opt-in telemetry

v0's roadmap lists this as "todo" — but the code already ships it (doc-rot of exactly the kind FACTS exists to catch). telemetry.mjs keeps always-local metrics — event counts, last-100 scan durations + file counts, error categories, a UUID installId — at ~/.facts-tree/metrics.json, with remote pingback gated behind TELEMETRY_URL + explicit opt-in and a hard rule to never record paths or names. v2 flies blind on which surfaces get used. Path: port the privacy contract verbatim; tune the IA with evidence. Lift: medium.

Later · hygieneAPI

10 · Always-fresh artifact on disk

Every v0 scan auto-writes facts-tree.json next to the project — a machine-readable snapshot that's always current without a separate command. Path: have the serve/dashboard mode re-emit agent.json + the pack on each scan so the in-repo artifact never goes stale. Lift: small.

Later · guardrailUX

11 · "Simple mode" + first-value as a regression test

v0 is dense yet starts in five seconds; v2 risks the "platform tax" — more power, slower start. Path: a guided first-run + a density/simple toggle, and a standing rule: every new v2 feature is measured against "did time-to-first-value get worse?" Treat v0's 5-second start as a regression test, not a memory. Lift: ongoing — a discipline, not a ticket.

What the two audits agree on

  • They tie on the human stuff. Both score 3/4 accessibility (real skip links, ARIA, focus) and pass the anti-slop test. Neither is a generated template, both are hand-built developer tools.
  • v2's lead is entirely "systematisation." It wins theming 4 vs 3 (a real CSS-variable token system vs v0's hardcoded Tailwind utilities) and edges anti-patterns, the dividends of types and tokens, not of taste.
  • Both have a mobile weak spot, for opposite reasons. v0 is desktop-only (live: a 900px breakpoint that hides the sidebar; the shell renders 1254px clipped inside a 375px viewport, 19 sub-44px touch targets), while v2 reflows its content fine but hides its 8-tab nav on mobile with no menu. Mobile is the shared homework: navigation for v2, the whole layout for v0. (The live pass corrected an earlier guess that v2's tables overflow, they don't.)
  • Performance splits on root cause. v0 loads Tailwind from a CDN at runtime (FOUC, offline-broken, network-bound), a P1 for a "self-contained" viewer; v2 ships every tab in the first-paint bundle (~96 KB gz, no route splitting). Different fixes, same symptom: it could be faster.
  • The irony holds at the pixel level. v0 ("v1.0.0") and v2 ("v0.1 alpha") are only 4 points apart on UI quality, yet a generation apart on the architecture beneath the pixels.
The CTO read

What this evolution tells you.

1

The team can self-critique and rebuild.

They commissioned a 200-point audit on their own work, accepted a 123/200, and acted on the architecture proposal rather than defending the prototype. That's a strong engineering-culture signal.

2

The bet is sound, the maturity is early.

The concept is validated (v0 worked; people used it). The v2 architecture is genuinely good. But it's alpha — expect rough edges, doc/code drift, and unfinished surfaces. Fund it like an early platform, not a finished product.

3

The moat is the contract, not the UI.

The durable asset is the typed spec + the isomorphic engine + FactsPack — the things that let one analysis serve humans, CI, and AI without drift. UIs are replaceable; that core is the leverage.

4

The trajectory is "act," not just "describe."

v0 described a repo. v2 is moving toward acting on it — the Change Verdict reviews a PR; the roadmap points at a bug-to-PR pipeline. That's the line from "viewer" to "agent platform."
