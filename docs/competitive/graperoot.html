1 · What it is & positioning

GrapeRoot is a retrieval + pre-injection layer that wraps an existing agent CLI. Instead of letting the agent explore the repo with tool calls, it builds a semantic graph, ranks the relevant files for your question, and packs them into the prompt before the model sees it — cutting exploration round-trips, turns, and tokens. Savings compound across a session because the tool remembers what was read/edited/queried.

Commercial open-core: the launcher scripts (bin/) are Apache-2.0 and open; the core graperoot graph engine is proprietary, shipped as a PyPI wheel, with a paid Pro tier at graperoot.dev/graperoot-pro.

2 · The “Dual-Graph” approach

info_graph.json

The static semantic graph: files, symbols, import relationships. Built by scanning the project. Answers “what is structurally relevant to this question?”

chat_action_graph.json

The dynamic session memory: reads, edits, queries, decisions during the conversation. Files you’ve touched get prioritized next turn — this is what makes context “compound.”

context-store.json

Cross-session persistence of decisions/tasks/facts, re-injected at the start of the next session. Optional CONTEXT.md for free-form notes. Continuity across conversations.

Wrapper + pre-injection

You run dgc instead of claude. It auto-starts & registers an MCP server, then injects ranked files into the prompt. (“Always use dgc, not claude” — bare claude gives MCP-connection errors.)

3 · Features

  • Pre-injection (push) context — ranks & packs relevant files into the prompt with no extra tool calls; the headline mechanism.
  • Compounding memory — per-turn (action graph) + cross-session (context store).
  • MCP tools for deeper agent-driven exploration: graph_read, graph_retrieve, graph_neighbors (and more).
  • Token-counter dashboard at localhost:8899, plus in-session count_tokens({text}) and get_session_stats() — surfaces live spend (on-brand for a cost tool).
  • Undo shield (bin/undo_shield.py) — guardrail around destructive edits.
  • Self-updating launcher — checks for a new version on every run and auto-updates.
  • Multi-CLI: Claude Code, Codex, Gemini, Cursor, OpenCode, GitHub Copilot. 11 languages: TS/JS, Python, Go, Swift, Rust, Java, Kotlin, C#, Ruby, PHP.

7 · Privacy & openness

  • Local processing — graphs, session data, and code stay on the machine.
  • Only outbound calls: a version check and a heartbeat (random install ID + platform only — no file names, no code). Telemetry was removed in favor of transparency.
  • Open-core caveat: launchers are Apache-2.0; the graperoot graph engine is closed and only on PyPI. The intelligence is not inspectable or forkable.

↳ Relevance to FACTS / FactsPack

GrapeRoot is the “retrieval & cost-delivery” benchmark — it optimizes which files load and when, where FactsPack optimizes how cheaply a fact is encoded. They attack disjoint halves of the token bill, so the pieces worth borrowing combine cleanly with FACTS’s strengths:

  • Pre-injection / push layer — the single highest-leverage borrow. Rank relevant files/symbols and inject a FactsPack-encoded context block before the agent asks. Selection (GrapeRoot) × encoding (FactsPack) beats either alone.
  • Compounding memory — a session action-graph + cross-session decision store, on top of FACTS’s existing static MEMORY.md and snapshots/diff.
  • Token budgets & read caps (DG_* vars) — predictable per-turn cost.
  • Live token accounting (count_tokens, get_session_stats, a dashboard) — FACTS should prove FactsPack’s savings in-session; this is its whole pitch.
  • Self-update + one-line installer — frictionless onboarding (FACTS needs a pnpm/tsx dance today).

Pitfalls to avoid that GrapeRoot exhibits: a hard wrapper dependency (“always use dgc”), a closed core (FACTS’s edge is an open, documented spec), and vendor-only benchmarks (ship reproducible ones).
