Section 1What FACTS is

The product in one breath, then the why.

  1. FACTS reads a codebase and writes a small, structured artifact an AI agent can read instead of the source.
  2. The pitch is token economics: a 1M-token repo compresses to a ~23K-token pack that still answers "where is X / who calls Y / what's risky" precisely.
  3. It is deterministic by design: same code in ⇒ byte-identical artifact out. No model, no randomness in the core.
  4. It serves two audiences from one computation: an AI agent (via the pack + an MCP server) and a human exec (via a dashboard).
  5. The core analysis is isomorphic — the same pure code runs in Node (CLI) and in the browser (the dashboard's scan worker).
  6. FACTS positions in the "structural / deterministic" camp (precise) vs the "embeddings / probabilistic" camp (scales), and aims for the uncontested center: deterministic + local + a compact tabular wire format + dual audience.
  7. Everything is local-first; analyze makes no network calls (a hard constraint). Network features (CVE lookups) are opt-in subcommands.
  8. The artifact is meant to be committable to the repo (.facts/), so it rides the diff and stays fresh per commit.
  9. This wave deepens FACTS from a file-level map into a graph-intelligence tool: symbol-level edges, queryable structure, ranked importance, and clustered modules.
  10. The through-line of the wave: make the dependency graph answer questions (F3), rank itself (F5), and price itself in tokens (F7) — all without an LLM.
  11. Nothing here changes the JSON artifact's version number (FACTS_SCHEMA_VERSION = 0.1.0); every JSON change is additive.
  12. The binary wire format (FactsPack) did bump, agent-v2 → agent-v3, because a new table changes what consumers decode.

Section 2Who it's for, and the job

Three users, one artifact.

  1. AI coding agents (Claude Code, Cursor, Copilot) — read the pack + call MCP tools instead of grepping the repo.
  2. CXOs / non-developers — open the dashboard and understand a codebase in under two minutes.
  3. Developers — use the CLI + dashboard to navigate, audit, and reason about structure.
  4. The job-to-be-done for an agent: "answer my question about this code in one cheap lookup, not ten expensive reads."
  5. The job for a CXO: "is this codebase healthy, what does it do, and what's risky" — answered with clickable evidence, not an unfalsifiable score.
  6. The graph-intelligence wave serves the agent (new MCP tools + pack tables) and the CXO (a new Modules dashboard tab) from the same metrics.
  7. "Evidence-first" is the design law: every claim resolves to a file:line or a clickable source, never a vibe.
  8. F3's free-text query is for agents that want to ask in English without learning a verb grammar; it stays deterministic so it never hallucinates an answer.
  9. F5's importance answers "what should I read first?"; communities answer "what clusters together?"; impact answers "what breaks if I touch this?".
  10. F7's token tools answer "will this fit in context?" / "how much will reading this cost?" — the literal currency of agent work.

Section 3The monorepo at a glance

A pnpm workspace: pure isomorphic packages, plus Node/browser adapters, plus apps.

  1. packages/spec — the schemas (Zod) + shared types + the canonical MCP tool/verb tuples. The single source of truth for shapes.
  2. packages/walker — walks the filesystem (via an injected FactsFS), yields files. Pure + isomorphic.
  3. packages/parsers — language detection + parse helpers.
  4. packages/extractors — per-file AST extraction: imports, symbols, refs, routes, env vars. Babel-based, pure-JS (no WASM/native).
  5. packages/graph — builds the dependency graph, the caller index, the symbol graph, and (new) the metrics. Pure.
  6. packages/scanners — secrets, licenses, TODOs, dependencies, vulnerabilities, token cost. Pure.
  7. packages/intent — infers a human one-liner of what the project does.
  8. packages/core — the orchestrator: composes walker → extractors → graph → scanners into the artifacts. Also hosts the query engine, MEMORY builder, diff, review, diagram.
  9. packages/factspack — the FactsPack codec: encode() / decode() for the columnar text format.
  10. packages/emit — Node-side writers + the agent→pack encoder + the human→viz converter. Where I/O lives.
  11. packages/emit-browser — the browser-side writers (File System Access API).
  12. packages/fs-node / packages/fs-memory / packages/fs-browser — the three FactsFS implementations (disk, in-memory for tests, browser).
  13. packages/skills — renders agent instruction files (AGENTS.md / Claude / Cursor / Copilot) from the artifact.
  14. packages/ui-theme — design tokens (colors, type, spacing) + the diagram CSS vocabulary, shared by the dashboard.
  15. apps/cli — the factstack binary. Node + Deno compatible. The primary surface.
  16. apps/mcp-server — the Model Context Protocol server; exposes the artifact as MCP resources + tools over stdio.
  17. apps/ui-remix — the React-free Remix v3 dashboard (the exec/dev UI).
  18. apps/chrome-ext / apps/vscode-ext — thin client integrations.
  19. The dependency direction is strict: apps depend on packages; pure packages never depend on Node-only ones.
  20. The wave touched ~29 files across 9 packages/apps, plus 12 new files — all green together.
  21. The build is source-served in dev: packages export ./src/*.ts as main, so a change in graph is live in core without a build step.
  22. Tests run with Vitest per package; the workspace runs them with pnpm -r test.
  23. Typechecking is per-package tsc --noEmit against a shared tsconfig.base.json with exactOptionalPropertyTypes: true (strict optionals).
  24. The whole workspace typechecks clean (19 projects) and runs 947 tests green after this wave.

Section 4The eight design invariants

The guardrails. Every change in this wave was checked against them.

  1. INV1 — Tier purity. spec/walker/parsers/extractors/graph/scanners/intent/core/factspack/emit-pure are pure + isomorphic: no node:*, no fetch, no wall-clock, no randomness, no I/O.
  2. The new graph/metrics.ts obeys INV1: it imports only types, uses only arithmetic, and touches no clock or RNG.
  3. INV2 — Determinism. Same input ⇒ byte-identical output. Fixed iteration counts, stable tie-breaks on a sorted key.
  4. PageRank uses a fixed 30 iterations (never "loop until converged", which would vary by platform rounding).
  5. Communities use a fixed 10-pass label propagation with lowest-label tie-breaks, processed in path-sorted order.
  6. INV3 — No model in the core. FACTS never calls an LLM. "Natural language" is resolved by deterministic entity-matching against real graph names.
  7. The F3 free-text mapper (query-nl.ts) honors INV3: it tokenizes + matches against real entity names + picks a keyword template; on doubt it returns a "did you mean" list, never a guess.
  8. INV4 — Additive schema evolution. New JSON fields are .optional() / .default() so old artifacts still validate; FACTS_SCHEMA_VERSION stays 0.1.0.
  9. F5's importance/community are .optional() on the node schema — pre-F5 artifacts load unchanged.
  10. A FactsPack table change bumps the pack schema name (a separate version axis); that's why this wave moved agent-v2 → agent-v3.
  11. INV5 — Single sources of truth. Query verbs live in one tuple (QUERY_VERBS); MCP tool names in one tuple (MCP_TOOL_NAMES). Add to the tuple first; tsc points at every site to change.
  12. Adding impact (F5) and count_tokens (F7) followed INV5: edit the tuple, then fix what tsc flags.
  13. INV6 — analyze makes no network calls. Held: nothing in the wave adds a fetch to the analyze path.
  14. INV7 — Browser parity. Pure features run identically in the browser scan worker; the new metrics do too (they're pure).
  15. INV8 — Token-first responses. New tabular agent responses ship as FactsPack (the F3 subgraph, the get_outline refs).
  16. The invariants are not aspirational comments — they are enforced by tests (determinism re-runs, schema round-trips) and by the type system (the tuple satisfies clauses).

Section 5How a scan works (the analyze pipeline)

analyze(fs, opts) in packages/core/src/index.ts — the spine.

  1. Phase 1 walks every file via the injected FactsFS (so the same code works on disk, in memory, or in the browser).
  2. Per file: detect language, count LOC + bytes, estimate token cost, gzip size (via an injected callback so core stays isomorphic).
  3. For JS/TS/Astro: parse once with Babel and share that AST across extractors (imports + symbols + refs) — parse-once, not parse-per-extractor.
  4. Imports are extracted as raw records: the module source ('./a'), the kind (import/type-import/dynamic/require), the line, and (new this wave) the local binding names.
  5. Symbols (declarations) are extracted with name, kind, line span, exported flag, and docstring.
  6. F2's identifier refs (call/read/jsx/type-ref) are captured per file, but only when --symbols is passed (the gated rollout).
  7. Secrets, licenses, TODOs, env vars, routes, and dependency manifests are scanned in the same per-file loop.
  8. After the walk, the resolver context is built: the set of project files, workspace package index, and tsconfig path aliases.
  9. buildDependencyGraph turns resolved imports into file edges (from importer → imported), detecting cycles with Tarjan's SCC.
  10. buildCallerIndex inverts the edges into "who imports me" and backfills node.callers.
  11. New (F2 fix): the imp.resolved backfill (turning './a' into src/a.ts) now runs before the symbol graph is built — previously it ran after, starving the resolver.
  12. New (F5): computeMetrics(depGraph) runs right after the caller backfill and writes importance + community onto the shared graph nodes.
  13. Because both the agent and human artifacts spread the same depGraph object, the metrics land on both for free (no double computation).
  14. The symbol graph (F2) is built next, but only under --symbols; otherwise the symbol arrays stay empty (and old consumers are unaffected).
  15. New (F10): buildRationale links NOTE/HACK/FIXME/TODO/XXX comments + docstrings to the enclosing symbol — coexisting in the same assembly.
  16. Broken imports + cycles are surfaced as risks after the resolved-backfill.
  17. The CSS audit runs over collected stylesheet sources; the dependency/vuln data is assembled; capabilities are inferred.
  18. The agent artifact is assembled (full graph incl. symbol arrays + metrics + rationale); the human artifact is assembled (file graph, no symbol arrays).
  19. Risks are funneled through applyRewrite so CXO-readable prose replaces raw rule text where one exists (the original is kept on messageTechnical).
  20. The analyzer is deterministic end-to-end: walk order is path-stable, maps preserve insertion order, and every new ranking sorts on a stable key.
  21. Wall-clock time (generatedAt) is the only non-deterministic field, and it's injected at the adapter edge, not computed in pure code.
  22. The whole pipeline is one function with clearly-ordered phases; the wave inserted its steps at documented, tested seams.
  23. A regression test (analyze.test.ts) now asserts that a hub file (util.ts imported by two files) gets importance 1.0 on both artifacts — locking the F5 wiring.
  24. A second regression test locks the F2 fix: an imported ref resolves at confidence 0.9 (the "import-resolved" tier), proving specifiers + ordering both work.

Section 6The artifacts FACTS writes

What ends up in .facts/.

  1. agent.json — the full machine artifact: files, graph (nodes/edges/cycles/symbols/metrics), routes, risks, config, docs, rationale.
  2. agent.pack — the same data in FactsPack (token-lean columnar text); the format agents actually read.
  3. agent.jsonl — a streamable companion (one FileOutline per line).
  4. human.json — the dashboard's data shape (a viz-friendly projection; file graph only).
  5. MEMORY.md — a 2–10 KB compact brief an agent reads on session start: one-liner, at-a-glance, capabilities, entry points, routes, key files, modules, open risks.
  6. snapshots/ — dated baselines used by since and review_change to diff against prior state.
  7. A --minimal mode writes only the AI-first core (pack + human.json + MEMORY.md) for fast per-commit refresh.
  8. All artifacts are additive-versioned: the JSON stays 0.1.0 forever as long as new fields are optional.
  9. The wave added two fields to agent.json graph nodes (importance, community) — both optional, both invisible to old readers.
  10. The wave added a 10th FactsPack table (nodeMetrics from F5; the F10 rationale table is the actual 10th) and bumped the pack schema to agent-v3.
  11. The dashboard's data (human.json / the baked inline blob) is produced by humanToViz(agent, human) — one transform feeds the static bake, the dev server, and the browser scanner.
  12. New (F5): that transform now also emits nodeMetrics (importance + community per path), so the dashboard consumes the core metrics rather than recomputing them.
  13. This is the load-bearing design choice of the F5 UI: one deterministic computation, two audiences — the agent and the dashboard can never disagree about importance.
  14. The artifacts are intended to be committed; the dashboard's static export bakes the JSON into a single self-contained HTML file.

Section 7FactsPack — the token-lean wire format

Why the agent reads a pack, not JSON.

  1. FactsPack is a line-oriented, columnar text format: each table is self-describing with an & name col1 col2 … header and - v1 v2 … rows.
  2. Repeated strings (file paths) are interned in an uppercase-named column via a @ K=value dictionary line, so a path written 50 times costs its bytes once.
  3. Unique-per-row values (a primary key path) stay literal — interning a unique value would waste a dictionary line per row.
  4. Short enums (kind/status/severity/confidence) stay literal — the dictionary overhead would exceed the savings on values under ~10 chars.
  5. The header line carries the producer, the schema name, a snapshot id, and a row count; consumers pin the schema name and reject a mismatch.
  6. On real data the pack is ~46× smaller than the equivalent JSON in tokens (the whole repo's structure in ~23K tokens vs ~1.07M tokens of source).
  7. The agent pack is now ten tables in a fixed order: files, imports, routes, risks, envs, declarations, symbols, calls, nodeMetrics, rationale.
  8. The order is part of the contract; a consumer can walk all tables or jump to a named one (every table has its own & line).
  9. New (F5): the nodeMetrics table carries path (literal PK) + imp (importance) + comm (community); it skips nodes with no metrics.
  10. New (F2): the imports table gained a conf column (edge provenance) back in agent-v2; the symbols and calls tables carry the symbol graph.
  11. The decoder preamble doc (docs/FACTSPACK_PROMPT.md) is a generic grammar primer — it teaches the syntax, not specific columns — so new tables need no doc change to be decodable.
  12. A pure round-trip test asserts the pack decodes back to the expected row counts per table, and that null values serialize as a bare -.
  13. The "all tables in fixed order" test now checks all ten tables, including the new nodeMetrics and rationale (a coverage hole the review closed).
  14. FactsPack is also the format for per-tool MCP responses (query, get_outline, list_risks, etc.) so an agent learns the columns once and reuses them.
  15. Per-tool packs carry their own schema names (query-graph-v1, outline-v2, subgraph-v1) advertised by the server's version block.
  16. FactsPack is pure and isomorphic — encoding/decoding runs in the browser exactly as in Node.

Section 8F1 — edge confidence (provenance)

Shipped earlier; the substrate the wave builds on.

  1. Every graph edge carries a confidence: extracted (read directly from source), inferred (resolved/deduced), or ambiguous (name-match only).
  2. The enum is ordered most→least certain so it can drive a threshold filter.
  3. File import edges are always extracted (they're literally in the source).
  4. Symbol edges (F2) carry the interesting confidences: same-file ⇒ extracted, import-resolved ⇒ inferred (0.9), single-global-match ⇒ inferred (0.7), multi-match ⇒ ambiguous (0.4).
  5. An optional confidenceScore (0..1) rides alongside for the inferred/ambiguous tiers.
  6. The schema default (extracted) keeps pre-F1 artifacts valid on read (INV4) so the JSON version never moved.
  7. A --min-confidence filter on queries keeps only edges at least that certain; it's a no-op until F2 produces non-extracted edges.
  8. MEMORY shows an edge-confidence line only when there are uncertain edges — no "100% extracted" noise.
  9. The pack's conf column is literal (3 short values; interning wouldn't pay).
  10. F1 is the reason the graph can say "I'm sure" vs "I'm guessing" — a property embeddings-based tools structurally cannot offer.
  11. F5's impact verb is confidence-aware: it can be told to traverse only edges above a confidence floor.
  12. Confidence is the connective tissue of the wave: F2 produces it, F3 filters on it, F5 can weight by it.
  13. The whole confidence model is deterministic — the same ref always resolves to the same tier.
  14. It is also honest about its limits: a name that collides across many files is marked ambiguous, not silently guessed.

Section 9F2 — the symbol graph

Declarations as nodes, references as edges.

  1. F2 moves beyond file-level imports to a symbol graph: nodes are declarations (functions/classes/methods/components), edges are references.
  2. A symbol's stable id is path#name@startLine — path + name + line disambiguates overloads and same-named decls.
  3. The id is built by one function (symbolId()) so every consumer agrees on the format.
  4. Edge kinds are call, read, jsx, type-ref, implements, extends.
  5. The resolver (symbol-resolver.ts) joins per-file refs against declarations + the import graph to produce the edges.
  6. Resolution tiers: same-file decl ⇒ extracted; import-resolved target ⇒ inferred 0.9; one global match ⇒ inferred 0.7; many matches ⇒ ambiguous 0.4 (lowest id chosen).
  7. It is pure + deterministic: candidate lists are id-sorted, the enclosing "from" symbol is the innermost span, edges dedupe keeping the strongest.
  8. Output is sorted: symbol nodes by id, symbol edges by (from, to, kind).
  9. The symbol graph is gated behind --symbols until it stabilizes; off by default so the per-file ref walk only runs when asked.
  10. When off, the symbol arrays are empty and the artifact's defaults apply — pre-F2 consumers are unaffected.
  11. The pack carries it as two tables: symbols (id, path, name, kind, span, exported) and calls (from, to, kind, conf).
  12. Known honest gaps: dynamic dispatch isn't inferred; default/namespace imports resolve only via the global fallback; module-top-level refs (outside any decl) are dropped.
  13. The resolver has 9 unit tests covering each tier + determinism + the enclosing-span logic.
  14. F2 is the substrate for everything downstream: F3 queries it, F5's symbol-level reach uses it, get_outline surfaces it.

Section 10The F2 follow-up — two real bugs caught by dogfooding

The unit tests were green while a whole confidence tier was dead in production. End-to-end dogfooding caught it.

  1. Bug 1 — empty import specifiers. The import extractor only recorded the module source ('./a'), never the named bindings (helper).
  2. So ImportDecl.specifiers was hardcoded empty in core, and the resolver's 0.9 "import-resolved" tier could never fire — every cross-file ref silently fell to the 0.7 guess tier.
  3. The fix: the extractor now captures the local binding names from each import declaration's specifiers (default + namespace + named).
  4. It captures the local name (the alias the file actually uses), because that's what identifier refs match against.
  5. Aliased imports (import {x as y}) keep the alias and gracefully fall to the lower tier — a documented, acceptable v1 gap.
  6. The deduper now unions names when the same module is imported twice, instead of dropping the second import's names.
  7. Core now threads those names into ImportDecl.specifiers (was []).
  8. Bug 2 — ordering. buildSymbolGraph ran before the imp.resolved backfill, so every import looked unresolved at resolution time even with specifiers present.
  9. The serialized artifact looked correct because the backfill mutated it after the symbol graph was built — hiding that the consumer saw null.
  10. The fix moved the resolved-backfill earlier, before buildSymbolGraph, so the resolver sees real targets.
  11. Both bugs had to be fixed for the 0.9 tier to fire; the dogfood edge went 0.7 → 0.9 once both landed.
  12. The lesson, encoded as a comment: unit tests that hand-build fixtures can pass while the real pipeline shape is broken; a pipeline-level regression test is what actually guards it.
  13. A new analyze.test.ts case asserts an imported ref resolves at exactly 0.9 — it would fail if either bug regressed.
  14. This wave also completed the deferred F2 item: get_outline now returns a refs table (outline-v2) of a file's outgoing symbol edges with confidence.

Section 11F3 — the declarative query engine

One small engine; the old verbs become sugar over it.

  1. F3 replaces ad-hoc verb code with one traversal primitive (runGraphQuery) over a unified adjacency of file edges + symbol edges.
  2. The two id-spaces (file paths vs path#name@line symbol ids) never share an edge, so a file seed naturally walks import edges and a symbol seed walks symbol edges.
  3. A GraphQuery has: a start selector (by id/glob/name/kind), a traverse (direction out/in/both, edge-kind filter, max depth), a where filter, a select (nodes/edges/subgraph), and a limit.
  4. The engine builds direction-aware adjacency, runs a depth-bounded BFS, applies the where-filter, and returns a connected subgraph.
  5. It's deterministic: adjacency is built from sorted neighbor lists, results are id-sorted, ties break on id.
  6. Capping is explicit: when limit drops nodes, the result carries a truncated flag — never a silent drop.
  7. The four legacy verbs (callers/imports/cycles/orphans) keep their tuned implementations; a parity test proves the engine reproduces callers and imports exactly.
  8. That's the anti-drift contract the plan wanted, achieved without a risky rewrite of the battle-tested verbs.
  9. New verbs added: neighbors (adjacent nodes, direction-controlled), references (who references a symbol), implementers (who extends/implements a symbol), path-between (shortest directed path).
  10. path-between is a deterministic multi-source BFS that explores neighbors in id order so the reconstructed path is stable.
  11. references restricts to call/read/jsx/type-ref edges; implementers restricts to implements/extends — so each answers a precise question.
  12. Verb resolution is forgiving: a target string matches an exact id, then a symbol/file name, then a path suffix — agents don't need to know the exact id.
  13. The engine + verbs have 13 unit tests (parity, symbol verbs, subgraph, where-filters, truncation, determinism).
  14. F5's impact verb reuses this engine's in-edge adjacency — "one engine," exactly as the plan intended.
  15. The verb set is single-sourced in QUERY_VERBS; adding a verb makes tsc flag every dispatch site.
  16. The structured GraphQuery is also exposed directly via the new query MCP tool, so agents can express custom traversals.

Section 12F3 — free-text → plan (no LLM)

English questions, deterministic answers.

  1. query-nl.ts maps a free-text question to a query plan — purely, with no model (INV3).
  2. It tokenizes the question, keeping identifier + path + symbol-id characters, and matches tokens against real entity names in the graph.
  3. Templates are chosen by keyword cues: "who calls X" / "what does X import" / "path between X and Y" / "unused files" / "cycles".
  4. Direction is inferred from phrasing: "who/what calls/uses/depends-on X" ⇒ incoming; "X depends on / imports" ⇒ outgoing.
  5. "what depends on X" beats the generic "depends on" cue — the stronger directional signal wins (incoming).
  6. When a name matches several entities, it returns a ranked candidate list ("did you mean…") rather than guessing.
  7. When nothing resolves, it suggests entities whose name/path contains a token — a graceful dead-end, not a hallucination.
  8. It's deterministic: token scan is left-to-right, the resolver returns id-sorted candidates, ties break on id.
  9. The plan is one of two shapes: a declarative GraphQuery (run via the engine) or a legacy verb call (for orphans/cycles/path-between).
  10. A stop-word list keeps question words ("who/what/the/of") from being mistaken for entity names.
  11. The mapper has 9 unit tests (directional cues, verb templates, did-you-mean, determinism).
  12. This is the deliberate line between FACTS and an LLM: FACTS offers a deterministic shortcut for the common shapes; real NL reasoning stays the calling agent's job.
  13. The interpretation string ("callers — nodes that reference X") is returned so the agent can confirm what FACTS understood.
  14. The CLI exposes it: factstack query "who calls buildMemory" works alongside the structured factstack query <verb> <target>.
  15. The CLI detects free-text vs verb by whether the first token is a known verb — no separate command needed.
  16. The MCP query tool accepts either q (free-text) or a structured query object, exactly one required.

Section 13F3 — the subgraph FactsPack + citations

The agent gets jump-to-source anchors.

  1. The query tool returns a connected subgraph as FactsPack (schema subgraph-v1).
  2. Four tables: nodes (id + path + kind + name), edges (from/to/kind/conf), citations (file:line#symbol anchors), and a 1-row meta.
  3. The citations table is the point: the agent can jump straight to src/auth.ts:1#helper instead of re-searching.
  4. The meta row carries the truncated flag + node/edge counts — so a capped result is never a silent drop (an explicit design law).
  5. Node metadata (path/line/name/kind) is recovered from the artifact's node lists, keyed by id, not by parsing the id string.
  6. Symbol ids carry their own line; file nodes have no line, so the citation line is null for files.
  7. The subgraph encoder interns the from/to symbol ids (they repeat across a symbol's edges) and keeps the node id literal (unique PK).
  8. The converter lives in pack-responses.ts alongside the other per-tool converters, following the established pattern.
  9. It was verified end-to-end against the real dogfood graph: "who calls helper" returns the right nodes/edges/citations with the import-resolved edge at confidence inferred.
  10. The subgraph format makes F3 the answer to the market-validated "NL code search with citations" pattern — but resolved deterministically.
  11. The free-text path lifts verb plans (orphans/cycles/path-between) into a node-list subgraph so the response shape is uniform.
  12. Format is selectable: pack by default (token-lean), format:"json" for the legacy shape.

Section 14F5 — PageRank importance

"What should I read first?" — graph-weighted, not raw in-degree.

  1. computeMetrics in packages/graph/src/metrics.ts computes a PageRank score per file over the import graph.
  2. Edges point importer → imported, so rank flows to the files everything depends on — a heavily-imported utility ranks high.
  3. This is strictly better than raw in-degree: a file imported by a few important files outranks one imported by many trivial ones.
  4. The power method runs a fixed 30 iterations with damping 0.85 — fixed, not convergence-stopped, so the count never varies by platform rounding (INV2).
  5. Dangling nodes (no out-edges) leak their mass; it's redistributed uniformly so the total stays ~1 and rank doesn't silently drain.
  6. The initial vector is 1/N (deterministic), not random — same trajectory every run.
  7. Nodes are processed in path-sorted order, so the result is independent of the analyzer's file-enumeration order.
  8. Adjacency is frozen into sorted arrays before iteration, so floating-point addition order is stable even if the edge list is reordered — a determinism belt-and-suspenders.
  9. The final scores are normalized by the max, so the top file is exactly 1.0 and others are relative — a clean 0..1 value for ranking and a dashboard bar.
  10. Scores are rounded to 4 decimals for determinism + compact serialization.
  11. Multi-edges (same from→to via import + type-import) are deduped so a dependency is weighted once.
  12. Self-loops and edges touching unknown nodes are ignored.
  13. Empty graph ⇒ empty maps; a single isolated node ⇒ importance 1.0 — the edge cases are explicit and tested.
  14. The maxRank === 0 guard prevents a divide-by-zero in degenerate graphs.
  15. Real-world validation: re-analyzing FACTS on itself ranks packages/spec/src/index.ts (the barrel everything imports) at importance 1.00 — exactly right.
  16. All 428 file nodes got a score (metrics are always-on for the file graph — cheap and unconditional).
  17. Symbol-level PageRank (over the symbol graph) is intentionally deferred behind --symbols; the file-level metric is the always-on default.
  18. The metric has 8 unit tests, including a "shuffle the edges, same result" test that proves the sorted-adjacency choice works.
  19. The 3-node hand-traced case (a→b, a→c, b→c) asserts c > b > a and c == 1.0 — a checkable anchor for the math.
  20. PageRank is a pure function of the graph; it touches no clock, no RNG, no I/O (INV1).
  21. It's computed once and consumed by MEMORY (key-files reorder), the pack (nodeMetrics), and the dashboard (Modules tab).
  22. The market signal: a leading CLI agent already does repo-map → personalized-PageRank; FACTS does it deterministically and emits it as a compact, agent-agnostic payload.

Section 15F5 — communities (label propagation)

"What clusters together?" — deterministic modules.

  1. Communities are computed by label propagation over the undirected import graph.
  2. Each node starts as its own community; in path-sorted order it adopts the most frequent label among its neighbors.
  3. Ties break on the lowest label value, so the result is independent of tally iteration order.
  4. Updates are asynchronous (visible within a pass) and run a fixed 10 passes with an early-out on no-change — never convergence-dependent.
  5. Communities are renumbered by smallest-member path, so an existing cluster's id is stable as the graph grows (adding an isolated file doesn't renumber everything).
  6. Determinism is tested directly: a "run twice + shuffle edges, byte-identical" assertion.
  7. A hand-traced two-cluster fixture asserts {a,b}=community 0 and {x,y}=community 1, numbered by smallest member.
  8. The plan deliberately chose label propagation over randomized Louvain — simple, fast, and INV2-safe (no seed needed).
  9. On FACTS itself, 428 files fell into 186 communities, of which 9 are real multi-file modules (the rest are leaf singletons).
  10. The biggest module (community 62) is 156 files — the core spec/analyzer cluster — which matches the real architecture.
  11. Communities are surfaced in MEMORY (a capped "Modules" section) and the dashboard (the Modules tab), each named by the module's most important member.
  12. A "module" requires ≥2 files; singletons aren't modules (every leaf file being its own cluster is noise, not signal).
  13. The community is a pure function of the graph — same input, same clusters, every time.
  14. It's stored as an optional integer on each graph node (INV4), invisible to pre-F5 consumers.
  15. Disconnected graphs naturally produce multiple communities; an empty graph produces none — both handled.
  16. The community id is what lets the dashboard color-group and what could later color the Sugiyama graph nodes (a flagged follow-up).

Section 16F5 — impact (blast radius)

"What breaks if I touch this?"

  1. The impact verb answers reverse reachability: everything that transitively imports/references the target.
  2. It reuses the F3 engine's in-edge adjacency — one engine, no new traversal code.
  3. For a file seed it restricts to import-kind edges; for a symbol seed it walks all symbol kinds.
  4. Its default depth is 3 (a meaningful blast radius), not 1 — a hub doesn't return the whole repo, but you see more than direct importers.
  5. Results are id-sorted (deterministic) and exclude the seed itself.
  6. It's wired through QUERY_VERBS → executeQuery → the CLI's needs-target list → the MCP refine (INV5, all sites).
  7. A regression test asserts impact at depth 3 reaches both hops, at depth 1 reaches only the direct importer, and a leaf has empty blast radius.
  8. The review caught a real bug here: the MCP schema defaulted depth to 1, which silently pinned impact to direct-importers-only from the MCP path.
  9. The fix removed the blanket schema default so executeQuery owns the per-verb default (1 for most, 3 for impact) — and a test now locks "impact with no depth reaches both hops".
  10. This is exactly the kind of behavioral bug that typecheck + the browser stay green on — the adversarial review earned its keep.
  11. Impact is the agent's "should I be careful?" tool and the reviewer's "what does this PR ripple into?" tool.
  12. It's confidence-aware: a min-confidence floor can exclude shaky edges from the blast radius.

Section 24Determinism — why and how

The property that makes FACTS trustworthy.

  1. Determinism means a code change produces a reviewable artifact diff — no spurious churn from run-to-run noise.
  2. It also means the agent and the dashboard, computing from the same input, always agree.
  3. PageRank's fixed iteration count is the canonical example: convergence-stopping would make the count vary by floating-point rounding across platforms.
  4. Sorted adjacency makes even floating-point addition order stable, so reordering the edge list can't change a score.
  5. Label propagation's lowest-label tie-break makes the result independent of tally iteration order.
  6. Community renumbering by smallest-member path keeps ids stable as the graph grows.
  7. The query engine sorts every result and breaks ties on id; path-between explores neighbors in id order.
  8. The free-text mapper scans tokens left-to-right and resolves to id-sorted candidates.
  9. The symbol resolver sorts candidates and dedupes edges deterministically.
  10. Wall-clock time is injected at the adapter edge; pure code never reads a clock.
  11. Determinism is tested, not assumed: metrics "run twice + shuffle, identical", subgraph "run twice identical", NL mapper "two runs identical".
  12. Rounding to fixed precision (4 dp for importance) closes the last floating-point gap before serialization.
  13. The whole wave was built to keep determinism as a first-class, tested property — not a nice-to-have.
  14. This is the structural advantage over embeddings-based tools: same input, same output, every time, provably.
