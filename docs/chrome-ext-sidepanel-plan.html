00TL;DR

The premise “a browser extension can’t run the analyzer” is only half true. @factstack/core is isomorphic, and the dashboard already runs the full analyze() in a Web Worker — for a local folder (File System Access) and for a GitHub repo (Trees API → in-memory FS). So the panel needs no backend, no native host, no WASM, no running CLI to analyze a project.

  • Reuse, don’t fork the engine. The entire data/analysis/token layer (core, graph, scanners, factspack, fs-browser, emit-browser, tokens.css) is browser-safe and reused as-is. Only presentation is new.
  • Two inputs, headline = active-tab GitHub. When the active Chrome tab is github.com/owner/repo, the panel offers one-click “Analyze this repo” — which also solves the “which project am I looking at?” problem. Local-folder analysis is the privacy-first companion mode; a bundled demo gives a zero-setup first run.
  • The UI is a remake, not a fold. The wide editorial layout provably breaks below 340px. We build a sidebar-specific surface (drill-down + ⌘K, list-first diagrams) over the same Dataset — keeping the editorial DNA (mono labels, tabular numerals, hairlines, dark navy + orange) while shedding the broadsheet geometry.
  • One unknown gates the local path. Whether showDirectoryPicker() works inside an MV3 side-panel page is unverified → a day-one throwaway spike decides it. The GitHub path is unaffected and ships regardless.

01Architecture

Three inputs feed one shared, isomorphic analyzer running in a Web Worker; its Dataset output is consumed by two independent presentation surfaces. The desktop dashboard stays untouched.

Already surface-agnostic (reused verbatim): the .pack wire format + decoder (packages/factspack), the pure analyzer tiers (core, graph, scanners, parsers, extractors, walker, intent), the FS abstraction + GitHub fetcher (packages/fs-browser — FsaBrowserFS, fetchGitHubToMemory()), artifact materialization (packages/emit-browser), and the design tokens (packages/ui-theme/tokens.css). Not reusable: the apps/ui-remix route/view tree (WebUI-specific) — the panel builds its own presentation on top of the same Dataset.

02Data acquisition & active-tab awareness

Your decision: support both local and GitHub, with a special path for “GitHub open in the main tab.” That blend is the spine of the panel.

The headline flow: analyze the active GitHub tab

  1. The panel reads the active tab’s URL (via chrome.tabs + a github.com host permission), and on tabs.onActivated/onUpdated keeps it current.
  2. If it matches github.com/<owner>/<repo>, the panel shows a primary “Analyze <owner>/<repo>” button — zero typing.
  3. On click → fetchGitHubToMemory(owner, repo) (existing, packages/fs-browser) pulls the tree + blobs into a MemoryFS → analyze() in the Worker → humanToViz() → render.
  4. Optional PAT (for private repos / rate limits) entered once; see the PAT-security risk before shipping.

This is the elegant answer to the “current project” problem: the panel infers context from what you’re actually looking at, instead of asking you to pick a folder every session.

03The UI remake — frontend-design / impeccable

The existing design is an editorial broadsheet: a centered content column plus a margin/footnote “wing,” multi-column tables, and 760px-hardcoded diagrams. The repo’s own tokens declare 340px as the minimum tested width; below that the math breaks (margin col → ~64px, 5-col tables → ~70px cells, the folder heatmap → 1px cells). Folding the desktop down produces the “shrunk desktop” look that reads as low-craft — the opposite of the goal.

Decision: build sidebar-specific views over the same Dataset — not responsive media-queries on the desktop routes. Each surface is honest to its width; zero regression risk to the shipping dashboard; the entire data/analysis/token layer is reused, so this is a presentation-only effort.

Navigation: drill-down stack + ⌘K

  • A drill-down stack (Home → section → detail) with a thin sticky .glass top bar (back button + mono breadcrumb + ⌘K + theme). Not a 9-tab row — 6 tabs already scroll at 400px.
  • Home is a launcher, not a route: a condensed Overview (health grade + 2×2 stat grid) above a single-column nav list where each row carries a live signal (Security → risk count + tone dot, Tests → pass %, History → 40px sparkline, Modules → count). You can triage without drilling.
  • ⌘K (already built) becomes the primary cross-cutting jump, extended with risks/vulns/modules as result types. Bind Ctrl+K too and surface it in the top bar.
  • Sub-views (Security has 3, Architecture has 3, Files has 2) become drill rows or a ≤3-chip mini-segment when labels are short.

The diagram ladder (the key move)

  1. List-first by default — ranked rows with inline proportional bars, built from the same computeSankey/treemap/graphAnalysis inputs. Legible at 320px, sortable, and the most agent- and CXO-readable form. The list is the evidence.
  2. Glance — a fluid viewBox SVG (Treemap, sparklines, mini-bars) only when it stays legible above a measured min size (ResizeObserver; below threshold, fall back to the list).
  3. Immersive — a full-panel-height pinch/pan/zoom sheet for the dependency graph, on demand (Phase 2). Never render a hardcoded-px SVG inline.

Design direction (tuned for a persistent thin panel)

  • Type: reuse tokens.css; cap max heading ~24px; body 13–14; data/mono 11–12; labels 10. Keep JetBrains Mono tabular numerals — the data density is the aesthetic.
  • Density & space: ~50ch measure; 44px min tap rows; flat 16px panel inset (drop the broadsheet gutter clamp); 4pt vertical rhythm; sticky section sub-headers on long scrolls.
  • Color: keep dark-first navy + safety-orange accent + yellow highlight verbatim — a terminal palette is right beside an editor. Dark is the correct default.
  • Surfaces: single column always; hairlines over boxes; paper over cards; glass only on the sticky top bar + ⌘K sheet.
  • Motion: restrained/fast; one signature motion = the drill push/pop slide; honor prefers-reduced-motion; no decorative animation.
  • Edges: every list has a clean mono empty note; truncate filenames middle-out (keep extension); must look intentional at both 320px and 400px (fluid, not fixed).

04MV3 shell — what actually has to change

Real blockers (must fix)
  • Inline boot script banned. The no-flash IIFE (index.html:31) is pinned by a SHA-256 hash today; MV3 ignores hashes and forbids inline scripts entirely → externalize to /assets/theme-init.js.
  • Absolute asset paths + path routing 404. Built HTML uses /assets/… and the router uses path-based pushState. Add vite base:'./' + a hash-routing adapter (#/security/vulnerabilities).
  • External origins move to the manifest. The HTTP-header CSP doesn’t carry over; MV3 grants remote access via host_permissions (github, api.osv.dev, raw.githubusercontent.com, fonts) — not connect-src.
Confirmed safe (no change)
  • css() adoptedStyleSheets is CSSOM — exempt from style-src. The strict no-inline-style posture is already MV3-clean.
  • Dynamic import() of the osvScanner chunk pulls a hashed module from the extension origin — covered by script-src 'self'.
  • No WASM in the build today (pure-JS parser); no wasm-unsafe-eval needed. (Add it only if tree-sitter WASM lands later.)
  • The inline dataset <script type="application/json"> is non-executable → MV3-safe.

Recommended: self-host fonts as bundled woff2 to drop the fonts.googleapis.com/gstatic.com dependency (removes a trust-surface origin and the FOUC race). Keep build:static (no sourcemaps) for the extension build. Run long analyses in the panel page context, never the service worker (MV3 SWs die after ~30s idle and would corrupt a run).

05Challenges & risk register

1 File System Access may not work in an MV3 side panel. Every local entry point routes through window.showDirectoryPicker(), which historically throws in extension page contexts. FAIL → page-context bridge (invoke picker on a real page, post the handle to the panel) or lean on the GitHub path for local-ish needs. GitHub flow is unaffected.

3 Ship-gate governance. No manifest, no privacy policy, no schema-version gate (the pack decoder explicitly does not enforce version → silent mis-render on drift), MV3 SW ephemerality, PAT in plaintext localStorage, install-time permission scrutiny. HighYes Add a parallel ship-gate workstream: privacy policy + least-privilege manifest; a pack version gate at decode (refuse + “re-analyze with a matching CLI” instead of rendering garbage); analyze in panel context; chrome.identity for GitHub auth before private-repo support.
4 Payload. 1.2 MB baked, but 68% is doc prose; not a first-paint blocker (JSON.parse ≈ tens of ms). The real risk is silently shipping doc bodies + hardcoded SVGs. HighNo Strip docs[].content from the panel profile (−650 KB), lazy-load on open; use the .pack fast-path; add a panel resident-payload cap to the bundle guard.
5 Two-UI drift / maintenance. A second presentation surface. MedNo Only presentation forks; data/analysis/tokens shared. All routes already take one Dataset prop → add a per-PR Dataset-parity check.
6 “Current project” detection. No mechanism exists in the repo; a panel beside an editor doesn’t know which local repo you’re viewing. MedNo Active-tab GitHub detection solves this for the GitHub path (your chosen headline flow). For local: persist last handle in IndexedDB + one-tap “re-grant & re-analyze”; accept the per-session prompt.

Honest residuals: (a) if the FSA spike fails, the “one folder-pick, no install” promise weakens. (b) GitHub-first routes repo bytes through GitHub’s servers, so “code never leaves the machine” doesn’t hold for that path — a tradeoff to communicate, not hide. (c) Chrome Web Store review timing is outside our control. (d) Shipping zero-telemetry (to honor the privacy brand) leaves us blind to field failures — a deliberate, accepted trade.

  • FSA spike — throwaway MV3 side panel: call showDirectoryPicker(); structured-clone a handle into a module Worker; read a file via FsaBrowserFS. Decides Risk #1.
  • Scaffold apps/chrome-ext into the workspace: manifest.json (MV3, side_panel, least-privilege perms), panel.html Vite entry, hash router, externalized boot script.

  • Active-tab detection spike: chrome.tabs + github.com host permission → parse owner/repo.
  • Privacy policy draft + permission inventory (ship-gate seed).

  • Panel shell: drill-down stack + sticky glass top bar + ⌘K; Home launcher with live signals.
  • Data: GitHub active-tab analyze + local folder (if spike passed) + bundled demo first-run.
  • Routes: Home (Overview), Modules, Files, Security, History — all list-first.
  • Diagram ladder tier-1 only (ranked lists from the shared compute). Strip doc bodies; panel bundle cap.

Pictures, prose, and live

  • Docs reader (lazy bodies), Review, Tests routes.
  • GitHub auth via chrome.identity (private repos); opportunistic localhost factstack ui live updates.
  • Chrome Web Store submission: listing, screenshots, privacy policy, permission justifications.
  • Optional: a content-script “Open in FactStack” affordance injected on github.com repo pages.

07Open questions to resolve in Phase 0

  • FSA-in-side-panel — the spike answer. Everything local hinges on it.
  • Does .pack alone drive the panel, or is human.json always needed? (humanToViz() takes both — confirm before committing to the .pack fast-path.)
  • Width floor — is 320px a hard target, or is 340–400px the realistic floor? (Affects whether the 2×2 stat grid + 44px rows stay comfortable.)
  • Audience weighting — CXO triager (lead with Home signals) vs developer (lead with Files/Modules/graph)? Shifts what Home leads with.
  • Immersive graph — build an in-panel pinch/pan canvas, or open the existing desktop DAG in a tab? (Cuts that effort from L to S.)
  • Permission scope vs conversion — github.com host access + tabs raises the install prompt scariness; confirm the least-privilege set for MVP.
