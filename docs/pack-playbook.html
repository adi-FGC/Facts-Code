The .pack playbook.

Everything worked out this session about FACTS's agent artifact: whether it actually makes an AI agent faster, how to make an agent prefer it over scanning, how to keep it fresh after every change, and how to make all of that universal through the web app. Written so a fresh agent can pick up the thread cold.

repo: factstack 347 files · ~1.07M tokens .pack: 93 KB ≈ 23.4K tok map/territory: ~46×

The whole thing in one breath

Yes, the pack makes an agent faster at locating a change and tracing what it touches — one lookup instead of a grep-hunt. The reliable way to make an agent use it is three legs: instruct + tool + refresh. But a stale pack lies, and the only universal, zero-install delivery is the web app writing the pack + rules files into any folder you open.

01 · what .pack isthe map, not the territory

A 93 KB index of a 1.07M-token codebase.

FACTS analyzes a project and emits .facts/agent.pack — a token-lean, columnar text format (schema agent-v4) built for an AI agent to read instead of the source. Thirteen tables, fixed order:

topagent-v4 — the curated head: the 20 most important files (PageRank + in-degree) so a reader gets the map before the raw tables.
filesevery file → language, LOC, token cost, bytes, status, churn, read-time
importsthe resolved dependency graph (from → to → kind → conf). Forward + reverse, each edge tagged with provenance. This is what grep can't give you.
routesURL/path → framework → method → handler file → symbol
risksseverity, category, rule, file:line, message — secrets, broken imports, TODOs, stale
envsevery env var → each read site (file:line, access kind, default)
declarationsevery top-level symbol → file, start/end line, exported? The table that makes "where is X" a one-liner.
symbolsF2 — every declaration as a graph node (path#name@line), kind, span, exported. Populated by analyze --symbols.
callsF2 — symbol → symbol references (call / read / jsx / type-ref / implements / extends), each with a confidence (extracted / inferred / ambiguous).
nodeMetricsF5 — per-file importance (normalized PageRank) + community (label-propagation cluster). The "what matters most / what clusters together" lens.
rationaleF10 — design "why" (NOTE / HACK / FIXME / TODO / XXX comments + docstrings) linked to the symbol it explains. Intent, not just structure.
entitiesF11 — whole-stack nodes beyond code: SQL tables/columns, Terraform/IaC resources, doc pages — each with a file:line anchor.
entityEdgesF11 — links between entities and code (reads / writes / defines / references), so "which file touches the users table" is a lookup.

Sizes that matter (agent-v4 self-analysis, 2026-06-12): the whole codebase is ~1.64M tokens of source across 472 files. The pack carries the structure of all of it — now including rationale, entities, and per-file metrics — in ~99K tokens, about 17× smaller. That 17× is the ceiling (the "load everything" case); the per-change win is more about precision than raw tokens, and the richer v4 tables trade some ratio for far more answerable questions.

03 · make the agent prefer itthree legs, not one

A rules file is a nudge. A tool is a pull.

Prose like "prefer the pack" can be ignored. The reliable enforcement is three legs together — and the third is the one everyone forgets.

LEG 1

Instruct

Agent-rules files at the project root tell the agent to query the pack before scanning. FACTS generates them.

factstack export-skills .
LEG 2

Tool

Connect the FACTS MCP so the agent reaches for get_outline/query_graph instead of grep. Tools beat prose. This is the strong lever.

.mcp.json → factstack-mcp
LEG 3

Refresh

Regenerate the pack on a trigger so it's trustworthy. A stale pack is worse than none — see below.

analyze --minimal / watch / hook

The staleness proof — live, in this repo

This repo's .cursorrules was generated 2026-05-26 and never refreshed. It now lies to the agent: it says 308 files and lists pre-v0.9 routes (/flow, /credentials) that no longer exist. Reality is 347 files and /architecture, /security. That is exactly why Leg 3 isn't optional.

leg 2 · wire the MCP (the strong lever)
// .mcp.json at the project root
{ "mcpServers": { "factstack": {
    "command": "factstack-mcp", "args": ["."] } } }

# MCP tools the agent then reaches for (all read the pack):
get_outline  query_graph  list_risks  review_change
read_memory  list_vulnerabilities  get_diagram  since
04 · keep it freshafter each change

Regenerate on a trigger, not on a whim.

factstack analyze --minimal is the fast path — it writes only agent.pack + human.json + MEMORY.md and skips the heavy artifacts. Pick a cadence by who's driving:

CadenceHowBest for
On savefactstack watch .solo dev editing live (chokidar, debounced)
Per agent turn REC.claude/settings.json Stop hook → analyze --minimalagent loops — regenerates once per turn, not per edit
Per commitgit pre-commit → analyze --minimal && git add .facts/agent.packteams / CI / PR review — pack rides the diff

Don't fire on every tool call — a PostToolUse hook on Edit|Write re-walks all 347 files on every save. Refresh at a logical boundary. The real scaling fix (not built yet) is incremental analysis: re-walk only changed files.

.claude/settings.json · the per-turn Stop hook
{ "hooks": { "Stop": [ { "hooks": [
  { "type": "command",
    "command": "factstack analyze --minimal . >/dev/null 2>&1 || true" }
] } ] } }
05 · the universal pathany project, no install

The web app is the zero-install delivery vehicle.

A CLI/MCP/hook works only where someone installed the toolchain. The FACTS web app analyzes in the browser and writes .facts/ straight into any folder you grant it via the File System Access API. That's what makes "any project you open" possible with no per-repo setup. Producer and consumer are split:

producer

Web app · analyze in browser

Open a local folder (FSA) or a GitHub repo. The scanner worker builds the artifacts client-side. No server, no CLI.

writes via FSA →
on disk

project/.facts/agent.pack

The Save flow writes the pack (default minimal: agent.pack + human.json + MEMORY.md) into the opened folder. This already works for any project.

packages/emit-browser/src/write.ts · fsa-writer.ts · lib/emitProfile.ts

read by →
consumer

The external AI agent

Claude Code / Cursor / Copilot working in that folder reads .facts/agent.pack + obeys the root rules files. The web app can't push to it — it keeps the artifacts present and fresh.

Two gaps to close for "any opened project"

Gap A — writes the data, not the "use it" instructions

The Save flow drops .facts/* but not the root rules files.

An agent opening a web-app-saved folder finds the pack but isn't told to prefer it — buildSkillsTo (.cursorrules / AGENTS.md / copilot) is still CLI-only.

Gap B — no auto-refresh trigger

The browser can't watch the filesystem like factstack watch.

It holds the FSA handle for the session, so it can re-scan + rewrite on demand — but not on literal keystroke.

The proposed build (reuses existing machinery)

Build #1 — keystone, contained

Wire buildSkillsTo into the browser Save.

Call the existing writer-agnostic buildSkillsTo(writer, agent, human) with the same FsaFileWriter, so every opened project also gets AGENTS.md + per-tool rules pointing at the fresh pack. Small add: an AGENTS.md format in @factstack/skills (today: Claude/Cursor/Copilot only) so it covers any agent.

Build #2 — auto-refresh

A "Keep .pack fresh" toggle.

Re-scan + rewrite on tab focus/visibilitychange (when you return from your IDE) and an optional interval, via the retained FSA handle. The web-native factstack watch.

The honest boundary: live MCP tools (Leg 2, the strongest pull) need a local factstack-mcp — that can't come from a web tab. So the universal path is rules-file + fresh-pack-on-disk, which any folder-reading agent can use. MCP stays the opt-in power-up for local setups.

06 · honest limitswhat would make this wrong

Where the pack shrugs.

  • ⟳
    Staleness.

    A snapshot. Edit without re-analyzing and it points at old lines and missing symbols. The whole of Leg 3 / Build #2 exists to fight this.

  • ◳
    It locates, it doesn't read.

    "Severity is in review.ts:23" — you still open and reason about the file. The pack removes the search, not the work.

  • ≈
    Resolution gaps.

    Only what the analyzer extracted: top-level declarations, resolved imports. Dynamic require, metaprogramming, or an unparsed language fall through. Grep still wins on raw string presence.

  • ⌱
    No incremental analysis yet.

    Every refresh re-walks the repo. --minimal is the fast path, but on huge repos per-edit refresh is too costly until incremental lands.

  • ⚇
    Web-app caveats.

    The FACTS tab must stay open and the folder permission granted; it refreshes on focus/interval, not on every keystroke.

Bottom line

The pack is a real speed-up where it counts — locating a change and its blast radius go from a hunt to a lookup. Make an agent use it with instruct + tool + refresh. Make it universal by having the web app write the pack and the rules files into any folder you open, and keep them fresh on focus. The day it stops helping is the day it goes stale — so the map is only ever as good as the last analyze.
