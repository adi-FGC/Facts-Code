    00 · The thesis

    Two buyers, one engine.

    FACTS is unusual: the same analysis output is valuable to a human who must judge a codebase and to an AI agent that must reason over it. Sell to both from one build. Willingness-to-pay shows up when the output stops being raw data and starts being a verdict — an opinionated, grounded answer to a question someone is already paying to answer (a slow human reviewer, or an agent burning tokens to re-derive structure).

    Buyer A

    Engineering leaders & developers

    Pay for risk visibility and reviewer leverage: "what does this change do to my system, is it safe to merge, is the codebase getting worse." The CodeRabbit / Greptile / SonarQube / CodeScene budget.

    Buyer B

    AI agents & agent operators

    Pay in tokens and accuracy: a fresh, structured, token-cheap context surface beats re-reading a repo every run. FACTS already emits the pack and speaks MCP — it can be the context layer agents call.

    02 · Recommended sequence

    Build order.

    Ship the verdict first (it's mostly composition and proves the "verdict not data" thesis), then the surface that delivers it, then widen to the AI buyer.

    NOW
    ① Change Verdict — corepackages/core/src/review.ts · fuse diff + blast-radius + structural deltas into a typed ChangeVerdict with a severity headline. Tests + dogfood on FACTS itself.
    NEXT
    ① surfacesfactstack review verb (Markdown + JSON) and a review_change MCP tool. Now both buyers can consume one engine.
    THEN
    ④ GitHub App / CI botDeliver the verdict as a PR comment automatically. This is the distribution surface that turns ① into a product people subscribe to.
    THEN
    ② Agent context delta-packBuild on since + agent.pack for incremental, always-fresh context. Strongest "AI pays" lever once a delivery endpoint exists.
    LATER
    ③ ⑤ ⑥ ⑦ ⑧Security posture report, drift tracking, onboarding pack, portfolio view, license gate — each reuses primitives the verdict already wires together.

    Why this order: the verdict is the wedge. It is ~70% existing primitives, it proves the "verdict, not raw data" thesis, and it is the one output both buyers want. Everything else is either a delivery surface for it (④) or a sibling that reuses the same composition (③⑤⑧).

    The one strategic caveat: bets that monetize best as a hosted service (②⑦) need auth + billing + an endpoint — set those up yourself; I'll build the engine behind them.
